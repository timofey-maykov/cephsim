# Точность

Точность разных частей модели разная. Раскладка PG проверена до каждой PG. Время recovery проверено одним реальным событием.

| Часть | Как проверена | Результат |
|-------|---------------|-----------|
| CRUSH: firstn, indep, классы, tunables | `crushtool --test`, 4 096 входов на правило | совпадает |
| CRUSH: MSR (`msr_indep`, `msr_firstn`) | `crushtool --test` на синтетике | совпадает |
| reweight группы OSD, CRUSH-вес 0 | `crushtool --test --weight`, `--reweight-item` | совпадает |
| expand: новые бакеты, теневые деревья | `crushtool --add-item` + `--set-subtree-class` + `--rebuild-class-roots` | совпадает |
| новое правило | `crushtool --create-replicated-rule` | совпадает |
| OSDMap: pps, upmap, up/exists | `osdmaptool --test-map-pgs-dump-all` и `pg ls` на реальных снимках | совпадает |
| доступность (inactive, incomplete) | следует из acting-наборов `pg ls` и правил Ceph | по определению |
| объём переезда | следует из раскладки и `num_bytes` PG | точный при точной раскладке |
| время recovery | back-test на реальном восстановлении (кластер A) | 16,0 ч против факта 17,7 ч |
| конкуренция с клиентами | не сверялась с фактом | модель по исходникам mClock |
| EC на реальных пулах | **не проверено: EC у нас нет** | см. ниже |

## Раскладка PG

### crushtool

`testdata/verify-crush.sh` (нужен docker, образ `quay.io/ceph/ceph:v20`) строит синтетическую карту: 3 стойки × 4 хоста × 12 OSD, классы hdd и ssd. В ней 6 правил:

| id | Правило | Тип |
|----|---------|-----|
| 0 | `chooseleaf firstn 0 type host` | replicated |
| 1 | `take root class hdd; chooseleaf indep 0 type host` | erasure |
| 2 | `choose indep 3 type rack; chooseleaf indep 2 type host` | erasure |
| 3 | `take root class ssd; chooseleaf firstn 0 type rack` | replicated |
| 4 | `take root class hdd; choosemsr 3 type host; choosemsr 2 type osd` | msr_indep |
| 5 | `choosemsr 2 type rack; choosemsr 2 type host; choosemsr 1 type osd` | msr_firstn |

Каждое правило сверяется в четырёх состояниях, плюс отдельно новое правило:

| Состояние | Что меняется |
|-----------|--------------|
| база | ничего |
| reweight | 10 OSD: 0, 0,5 и 0,3 |
| CRUSH-вес 0 | весь host-03, с пересчётом предков и теневых деревьев |
| +2 хоста | host-13 (hdd) в существующей rack2 и host-14 (ssd) в новой rack5 |
| новое правило | `rep_rack_hdd`: `--create-replicated-rule ... --device-class hdd` |

Итог - 25 проверок, все совпадают один в один:

```
  ✔ rule 0 база: 4096 x совпали
  ...
  ✔ rule 4 +2 хоста: 4096 x совпали
  ✔ rule 5 база: 4096 x совпали
  ✔ новое правило rep_rack_hdd: 4096 x совпали
```

### Реальные кластеры

`cephsim verify`:

| Снимок | Ceph | PG | upmap | vs osdmaptool | out 1 OSD | vs pg ls |
|--------|------|----|-------|---------------|-----------|----------|
| кластер A: 5 хостов, 105 OSD, rep 3 | 20.2 | 4 513 | 0 | ✔ | ✔ | ✔ |
| кластер B: 4 ряда, 33 хоста, 438 OSD, rep 2 и rep 3 | 17.2.6 | 19 649 | 8 251 `pg_upmap_items` | ✔ | ✔ | ✔ |
| синтетика | 20 | 4 608 | 0 | ✔ | ✔ | - |

Важно: сверка идёт по up-наборам (`--test-map-pgs-dump-all`). На кластере B во время backfill у 380 PG acting отличался от up из-за `pg_temp`. Сверка по acting дала бы ложные расхождения.

## Время recovery

Back-test один: кластер A, восстановление RGW-пула на SSD, 0,96 TB, 22,9 млн объектов (в среднем 41 KiB). Узким местом был один SSD-OSD.

| Модель | Время |
|--------|-------|
| факт | 17,7 ч |
| только предел по байтам | 6,6 ч |
| с пределом по объектам (калибровка по `ceph_pool_recovering_objects_per_sec`) | 16,0 ч |

Вывод: для пулов RGW с мелкими объектами время определяет число объектов, а не байты. Без предела по объектам время занижено примерно в 2,7 раза.

Чего не хватает:
- back-test на HDD: на кластере A в истории не было recovery на HDD;
- back-test на кластере B;
- back-test сценариев drain и expand на реальном событии;
- сверка модели mClock с фактическими задержками клиентов.

## EC

**На кластерах, где проверялся cephsim, EC-пулов не было** (все пулы replicated). Поэтому код для EC проверен только тестами и на синтетике.

| Что реализовано для EC | Чем проверено |
|------------------------|---------------|
| шард PG на OSD = 1/k байт PG | юнит-тесты |
| incomplete при живых шардах < k, inactive при < `min_size` | юнит-тест `TestAvailabilityHostDown` (EC 2+2) |
| позиции шардов: NONE вместо удаления OSD (indep) | порт `_remove_nonexistent_osds` и `_raw_to_up_osds`, сверка indep с crushtool |
| правила indep и MSR | crushtool на синтетике |
| k из `erasure-code-profile` (без профиля - `k = size − 2` с предупреждением) | не проверено на реальных профилях |
| `-new-rule erasure`, `-new-rule msr` | сверены шаги правил с исходниками Ceph; на реальных пулах не применялись |

Если EC-пулы появятся:
1. Снять снимок через `collect`: он сохранит профили в `ec_profiles.json`.
2. Выполнить `verify`: раскладка EC-пулов должна сойтись с `pg ls` по каждой позиции шарда.
3. Сделать back-test recovery хотя бы одного EC-пула. У EC другой профиль нагрузки: чтение k шардов на каждую восстановленную PG.

## Ограничения

**Модель:**
- считается up-набор, а не acting: `pg_temp` и `primary_affinity` в новой раскладке не учитываются. Доступность при этом считается по acting из `pg ls`;
- время recovery - время самого загруженного OSD. Задержки на peering, очередь резервирования backfill и `osd_recovery_sleep` отдельно не моделируются, они входят в калиброванную скорость;
- клиентская нагрузка - средняя по OSD класса, горячие OSD не выделяются;
- цена recovery-операции в mClock - одна операция на объект;
- с планировщиком wpq и в Quincy до 17.2.7 конкуренция с клиентами не моделируется;
- догон после noout считается по мгновенной `write_bytes_sec` в момент снимка.

**CRUSH:**
- только straw2-бакеты; straw, uniform, list, tree и legacy tunables (`choose_local_fallback_tries > 0`) отклоняются с ошибкой;
- id классов устройств в дамп CRUSH не попадают, их порядок восстанавливается по теневым бакетам. Нужно для id новых теневых бакетов при expand;
- weight set (choose_args) новых бакетов заполняется CRUSH-весом. После ребаланса balancer в режиме crush-compat пересчитает его сам.

**Сценарии:**
- expand: id новых бакетов предсказываются по правилам CrushWrapper для порядка «хост за хостом». При другом порядке добавления в кластере сменится, какие именно PG переедут, но не объём;
- pgnum: считается конечная раскладка. Постепенный подъём `pgp_num` с пределом misplaced 5% растягивает переезд, время - нижняя оценка;
- rolling: партии собираются жадно (first-fit) по порядку дерева. Это не обязательно минимальное число партий, но на проверенных топологиях оно совпадает с числом failure domain;
- снимок - момент времени: идущий backfill, временные upmap балансировщика и `write_bytes_sec` меняются.
