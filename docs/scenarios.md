# Сценарии

Каждый сценарий меняет копию состояния кластера из снимка и сравнивает «до» и «после». Что считается в каждом из них, описано в [model.md](model.md). Здесь - что делает сценарий, как его задать и как читать результат.

| Сценарий | Теряются копии | Двигаются данные | Главный вопрос |
|----------|----------------|------------------|----------------|
| [maintenance](#maintenance) | да, на окно | без `-noout` - да, дважды | можно ли выключить, сколько ждать |
| [failure](#failure) | да | да | переживёт ли кластер, не переполнится ли |
| [drain](#drain) | нет | да | сколько ехать, хватит ли места |
| [expand](#expand) | нет | да | сколько ехать, как заполнятся новые OSD |
| [rule](#rule) | нет | да | сколько ехать, хватит ли failure domain |
| [pgnum](#pgnum) | нет | да | сколько ехать, не упрёмся ли в предел PG на OSD |
| [rolling](#rolling) | да, партиями | нет (noout) | в каком порядке и сколько по времени |

## maintenance

Хост (или несколько) выключается на время работ и возвращается.

```bash
cephsim simulate -snap snap -action maintenance -target host-07 -noout -window 3h -compare
```

- **С `-noout`** OSD становятся down, но не out: данные никуда не едут. PG теряют копию на время окна. Записи, пришедшие за окно на эти PG, после возврата хоста догоняются recovery («догон»).
- **Без `-noout`** через `mon_osd_down_out_interval` OSD выйдут в out: данные уедут с хоста, а после возврата поедут обратно. Модель считает переезд один раз, отчёт пишет «туда и столько же обратно». Если окно короче переезда, данные начнут уезжать зря.

Как читать:
- `PG inactive` > 0 - выключать нельзя: часть данных станет недоступна на всё окно.
- `PG без запаса` - PG, у которых остаётся ровно `min_size` копий. Ещё один отказ во время окна - и они станут inactive. Если окно длиннее 4 часов, это предупреждение.
- `-compare` сравнивает варианты «с noout», «без noout, backfills 2» и «без noout, backfills 6» и помечает лучший.

Пример (кластер из 5 хостов, rep 3; один хост на 21 OSD, noout, 3 ч): 2 622 PG (58%) degraded и без запаса, inactive - 0. Вердикт «безопасно». Без noout переедет 20,4 TiB туда и обратно, это 5,5-10 ч.

## failure

Внезапная потеря хоста, стойки, ряда или отдельных OSD. OSD становятся down и out (reweight 0), CRUSH перекладывает их PG на оставшиеся OSD.

```bash
cephsim simulate -snap snap -action failure -target rack2
cephsim simulate -snap snap -action failure -target row2 -assume-clean
```

Как читать:
- `PG incomplete` - живых копий не осталось (для EC - меньше k шардов): данные потеряны до возврата OSD.
- `PG inactive` - копий меньше `min_size`: I/O к этим PG встанет до конца recovery.
- `макс. OSD` и `выше nearfull` - выдержат ли оставшиеся OSD новые данные. Если OSD превысят `backfillfull_ratio`, recovery остановится, если `full_ratio` - встанет запись на всём кластере.
- `PG undersized` - CRUSH не нашёл для PG достаточно failure domain. Пока OSD не вернутся, у этих PG будет неполный набор копий.

Пример (кластер из 4 рядов разной ёмкости, failure domain - ряд; потеря одного большого ряда, `-assume-clean`): inactive - 0, но данные переедут и в самый маленький ряд, его OSD заполнятся до 144%. Вердикт «нельзя»: запись встанет.

## drain

Плановый вывод навсегда: CRUSH-вес OSD становится 0, как при `ceph osd crush reweight osd.N 0` или `ceph orch host drain`. Веса хоста и стойки пересчитываются. OSD остаются up, поэтому копии не теряются: данные уезжают с живых OSD.

```bash
cephsim simulate -snap snap -action drain -target host-03 -backfills 3
```

Как читать:
- узкое место обычно сам выводимый OSD: всё уезжает с него, и отдача ограничена его слотами;
- `PG по-прежнему указывают на выводимые OSD (pg_upmap_items)` - upmap переопределяет CRUSH, и PG останутся на выводимом OSD. Их нужно удалить вручную (`ceph osd rm-pg-upmap-items <pgid>`) или дождаться, пока balancer их уберёт.

Пример (хост из 10 HDD по 18 TB на кластере с 400 OSD): 106 TiB, около 6,9 суток при `osd_max_backfills=1`. Время упирается в число объектов. 223 PG держатся на хосте через upmap.

## expand

Добавление хостов с OSD. Флаг `-add` повторяется, по одному на группу хостов.

```bash
cephsim simulate -snap snap -action expand \
  -add host=new,count=2,rack=rack3,osds=12,size=18T,class=hdd
```

Формат `-add`, ключи через запятую:

| Ключ | Обязателен | Что |
|------|------------|-----|
| `host=ИМЯ` | да | имя хоста; при `count` - префикс, хосты будут `ИМЯ-01`…`ИМЯ-NN` |
| `osds=N` | да | OSD на хост |
| `size=16T` | да | размер одного OSD: `T`, `TB` (10¹²), `TiB` (2⁴⁰), `G`, `GB`, `GiB` |
| `class=hdd` | нет, `hdd` | класс устройств |
| `count=N` | нет, 1 | сколько одинаковых хостов |
| `weight=W` | нет | CRUSH-вес одного OSD; по умолчанию размер в TiB, как при `osd_crush_initial_weight=-1` |
| `<тип>=ИМЯ` | да, хотя бы один | куда ставить: `rack=…`, `row=…`, `root=…`. Нужен хотя бы один уже существующий бакет; недостающие уровни создаются |

Что делается с копией CRUSH-карты - то же, что в кластере сделает `ceph osd crush create-or-move` (`CrushWrapper::insert_item`):
- OSD получают наименьшие свободные id;
- новые бакеты получают первый свободный id;
- теневые деревья классов (`host~hdd`) перестраиваются как в `rebuild_roots_with_classes`, со старыми id.

Это сверено с `crushtool --add-item` один в один, см. [accuracy.md](accuracy.md).

Как читать:
- `новые OSD ... заполнятся до X..Y%` - сколько данных CRUSH отдаст новым OSD. Если новые OSD заполняются сильно выше среднего, значит их бакет перевешивает в своём failure domain. Если ниже - failure domain уже полон, и данные упираются в правило;
- узкое место - почти всегда новый OSD на приёме.

План в отчёте ставит `norebalance` на время создания OSD, чтобы данные не поехали несколько раз по мере появления каждого OSD.

Пример (тот же кластер, +1 хост 12×18 TB): 169 TiB, около 6,8 суток. Новые OSD заполнятся примерно до 52% при среднем по HDD 33%.

## rule

Пул переводится на другое CRUSH-правило: существующее (`-rule`) или новое (`-new-rule`).

```bash
cephsim simulate -snap snap -action rule -pool rbd -rule replicated-hdd
cephsim simulate -snap snap -action rule -pool rbd -new-rule replicated,fd=rack,class=hdd
```

Формат `-new-rule`: первым идёт режим, дальше ключи.

| Режим | Как в Ceph | Шаги правила |
|-------|------------|--------------|
| `replicated` | `ceph osd crush rule create-replicated` | `take root[~class]; chooseleaf firstn 0 type FD; emit` |
| `erasure` | `ceph osd crush rule create-erasure` | `set_chooseleaf_tries 5; set_choose_tries 100; take; chooseleaf indep 0 type FD; emit` |
| `msr` | EC-профиль с `crush-osds-per-failure-domain` (Squid и новее) | `take; choosemsr (k+m)/per type FD; choosemsr per type osd; emit` |

| Ключ | По умолчанию | Что |
|------|--------------|-----|
| `fd=` | `host` | failure domain: `host`, `rack`, `row`, … |
| `class=` | нет | класс устройств |
| `root=` | `default` | корень |
| `per=` | - | msr: OSD на один failure domain |
| `name=` | `<пул>_<fd>[_<класс>]` | имя правила |

Проверки: replicated-правило нельзя назначить EC-пулу и наоборот, MSR - только для EC. Если failure domain меньше `size`, PG останутся undersized навсегда, и вердикт - «нельзя».

У нас все пулы replicated: режимы `erasure` и `msr` реализованы и сверены с `crushtool` на синтетике, но на реальных пулах не применялись.

## pgnum

Новый `pg_num` пула. `pgp_num` в конечном состоянии равен ему.

```bash
cephsim simulate -snap snap -action pgnum -pool backups.buckets.data -pg-num 8192
```

Как считается раскол. Объект с хешем h лежит в PG `ceph_stable_mod(h, pg_num)`. Номер PG зависит только от младших бит хеша, поэтому доля каждой старой PG в каждой новой считается точно перебором всех 2^bits значений. Это работает и при `pg_num` не степени двойки, и при уменьшении (слиянии PG). Байты и объекты PG делятся по этим долям, и каждый кусок переезжает с OSD старой PG на OSD новой.

Как читать:
- `PG на OSD в среднем X → Y` против `mon_max_pg_per_osd`. Если среднее выше предела, монитор отклонит команду. Если на каком-то OSD больше предела × 3 (`osd_max_pg_per_osd_hard_ratio`), лишние PG не создадутся и останутся activating;
- `pg_num не степень двойки` - часть PG будет вдвое больше остальных;
- при уменьшении PG сливаются по парам, с peering каждой: это дольше расчётного времени.

В реальности mgr поднимает `pgp_num` шагами и держит долю misplaced не выше `target_max_misplaced_ratio` (5%). Модель считает конечную раскладку: объём переезда точный, а время - нижняя оценка.

Пример (пул rep 2, 4096 → 8192 PG): переедет 64 TiB. По модели около 2 ч 42 мин, в реальности дольше из-за предела misplaced.

## rolling

Расписание обслуживания хостов с noout: какие хосты можно выключать вместе, в каком порядке и сколько это займёт.

```bash
cephsim simulate -snap snap -action rolling -window 2h -gap 15m
cephsim simulate -snap snap -action rolling -target row3 -window 1h -parallel 2
cephsim simulate -snap snap -action rolling -window 2h -assume-clean
```

Алгоритм:
1. Берутся хосты под `-target` (по умолчанию все) и сортируются по пути в CRUSH-дереве (`root/row/rack/host`), чтобы хосты одного failure domain шли подряд.
2. Каждый хост проверяется в одиночку: если его выключение даёт inactive или incomplete PG, он попадает в «нельзя» и в партии не идёт.
3. Остальные раскладываются first-fit: хост идёт в первую партию, где одновременное выключение всей партии не даёт inactive и incomplete PG и где меньше `-parallel` хостов.
4. Время партии - `-window`, плюс догон записей за окно, плюс `-gap` перед следующей партией.

При failure domain host получается по одному хосту на партию. При rack или row - целые стойки или ряды: на кластере из 4 рядов - четыре партии примерно по рядам.

Как читать:
- `✖ host - нельзя с noout (… только из-за PG, неполных уже сейчас)` - хост держит единственную живую копию PG, которые уже деградировали (идёт recovery или backfill). Блокировку снимет завершение recovery. Пересчитайте с `-assume-clean`, чтобы увидеть картину после HEALTH_OK;
- `✖ host - нельзя с noout (N inactive, M incomplete)` без пометки - проблема в правилах пулов или в размещении: этот хост нужно сначала выводить через drain;
- `без зап.` - сколько PG на время окна остаются с `min_size` копий.

Пример (кластер из 33 хостов в 4 рядах):
- в снимке идёт backfill, 250 PG с неполным acting, и 23 из 33 хостов сейчас выключать нельзя;
- с `-assume-clean` - 4 партии, около 8 ч 47 мин при окне 2 ч.
