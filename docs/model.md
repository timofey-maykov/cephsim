# Модель

Как cephsim получает каждое число в отчёте. Обозначения: `size`, `min_size`, `k` - параметры пула, «шард» - доля PG на одном OSD (1 для replicated, 1/k для EC).

## 1. Доступность

Считается по **acting**-наборам из `ceph pg ls`, то есть по тому, где копии лежат сейчас, а не где должны лежать. С `-assume-clean` берутся **up**-наборы: так будет после завершения текущего recovery.

Для каждой PG: `живых` = членов набора, которые не выключаются в сценарии.

| Состояние | Условие | Что значит |
|-----------|---------|------------|
| degraded | живых меньше, чем было | PG потеряла копию |
| incomplete | живых < 1 (replicated) или < k (EC) | данных нет до возврата OSD |
| inactive | живых < `min_size` | I/O к PG встаёт |
| без запаса | живых = `min_size` | ещё один отказ - inactive |

Дополнительно:
- `pg_undersized_now` - PG, у которых acting уже неполный в снимке;
- `pg_lost_already_undersized` - сколько из inactive и incomplete приходится на такие PG. Если это все, блокировку снимет завершение recovery.

В сценариях drain, expand, rule и pgnum копии не теряются: OSD работают, пока данные переезжают, и PG только remapped.

## 2. Раскладка PG

Для каждой PG всех пулов up-набор считается заново - и для состояния «до», и для «после». Повторяется `OSDMap::_pg_to_up_acting_osds` без `pg_temp`:

1. `pps` - номер PG в CRUSH: `ceph_stable_mod(ps, pgp_num)`, при флаге `hashpspool` - `crush_hash32_2(ps, pool_id)`.
2. `crush_do_rule` правила пула с весами `osd_weight` (reweight) и `choose_args` (weight set balancer) - порт `mapper.c`: straw2, firstn, indep, MSR, все tunables.
3. `_remove_nonexistent_osds`: несуществующие OSD убираются (для EC - заменяются на NONE).
4. `_apply_upmap`: `pg_upmap` и `pg_upmap_items`; пропускаются, если целевой OSD out.
5. `_raw_to_up_osds`: down OSD убираются (для EC - NONE).

Как меняется состояние «после» в каждом сценарии:

| Сценарий | Изменение |
|----------|-----------|
| maintenance без noout, failure | OSD down, `osd_weight` = 0 (out) |
| maintenance с noout | без изменений: данные не двигаются |
| drain | CRUSH-вес OSD = 0 во всех бакетах, включая теневые; веса предков и weight set пересчитаны, как `ceph osd crush reweight` |
| expand | новые бакеты и OSD в копии CRUSH-карты (`insert_item` + `rebuild_roots_with_classes`) |
| rule | у пула другой `crush_rule`; новое правило добавляется в копию карты |
| pgnum | у пула новые `pg_num` и `pgp_num` |

Почему свой CRUSH, а не `osdmaptool`: `osdmaptool --mark-out` принимает один OSD, а удаление OSD из CRUSH даёт другую раскладку (меняются веса бакетов, уезжают чужие PG). Правки карты (expand, rule) он не делает вовсе.

## 3. Переезд

Данные PG делятся на куски. Обычно кусок - это PG целиком. При смене `pg_num` куски - доли старых PG в новых (см. [scenarios.md](scenarios.md#pgnum)). Для каждого куска:

- **байт шарда** = `num_bytes` PG × доля куска × шард;
- **объектов** = `num_objects` PG × доля куска. У EC шард хранит кусок каждого объекта, поэтому объектов в шарде столько же, сколько в PG;
- каждый OSD, который есть в новом наборе и нет в старом, **принимает** шард;
- **отдаёт** шард первый член старого набора, который остался в новом и не выключается. Если такого нет - любой живой член старого набора. При drain отдаёт сам выводимый OSD, стоявший на этой позиции.

`moved_bytes` и `moved_objects` - сумма по всем новым копиям: при rep 3 и смене всех трёх OSD кусок считается трижды. `moved_pgs` - сколько PG после изменения получили хотя бы одну новую копию.

## 4. Заполненность OSD

```
после = (kb_used × 1024 + принято − ушло) / (kb × 1024)
```

`ушло` - шарды PG, которые покинули OSD. Выключенные OSD в расчёт не берутся. У новых OSD (expand) `kb_used` = 0, `kb` = размер. Пороги `nearfull_ratio`, `backfillfull_ratio`, `full_ratio` берутся из osdmap кластера.

## 5. PG на OSD

Число шардов PG на каждом OSD в раскладке до и после.
- **Среднее** - на OSD, которые up и in. С ним сравнивает монитор при `pg_num` и создании пула (`mon_max_pg_per_osd`).
- **Максимум** - на самом нагруженном OSD. Если он больше `mon_max_pg_per_osd` × 3 (`osd_max_pg_per_osd_hard_ratio`), OSD не создаст лишние PG.

## 6. Время recovery

Узкое место - OSD, который дольше всех принимает или отдаёт. Для каждого OSD берутся байты и объекты, `max(приём, отдача)`, и время - максимум из трёх пределов:

| Предел | Время | Откуда параметры |
|--------|-------|------------------|
| байты | байты / (`backfills` × слот MB/s класса) | калибровка или `-slot-mbps`, иначе hdd 40, ssd 150, nvme 300 |
| объекты | объекты / (`backfills` × слот об/с класса) | калибровка по пулам или `-slot-ops`; без них предела нет |
| mClock | (объекты × `cost_per_io` + байты) / (доля recovery × ёмкость OSD) | `meta.json` (ёмкость mClock) и калибровка (клиентская нагрузка) |

В отчёте у узкого места указано, какой предел сработал: «упирается в байты», «в число объектов» или «в ёмкость mClock».

Предел mClock от `osd_max_backfills` не зависит: на нём время одинаково при любых backfills. Это не ошибка: в Ceph с mClock `osd_max_backfills` не действует без `osd_mclock_override_recovery_settings`.

Если после переезда какой-то OSD превысит `backfillfull_ratio`, время - «не завершится».

## 7. Конкуренция с клиентами (mClock)

Подробно - в [calibration.md](calibration.md#mclock). Кратко:

- ёмкость OSD - `osd_mclock_max_sequential_bandwidth_{hdd,ssd}` байт/с;
- цена операции - `bandwidth / osd_mclock_max_capacity_iops` байт (на HDD около 500 KB) плюс её размер;
- спрос клиентов - (оп/с × цена операции + байт/с) / ёмкость;
- клиентам при идущем recovery достаётся не больше `res_c + (1 − res_c − res_r) × w_c / (w_c + w_r)`. Резервы и веса берутся из профиля (`mclock_common.h`);
- recovery получает `1 − min(спрос, доля клиентов)`, но не больше своего лимита.

Если спрос больше доли клиентов, появляется предупреждение: во время recovery у клиентов вырастут задержки.

## 8. Догон после noout

За окно записи на degraded PG не попадают на выключенные OSD. Их догоняет recovery после возврата хоста:

```
догон, байт = write_bytes_sec × окно × Σ(шард по degraded PG) / всего PG
время       = догон / (число выключенных OSD × backfills × слот MB/s)
```

`write_bytes_sec` - мгновенная скорость записи из `ceph status` в момент снимка. Если снимок снят в тихое время, догон занижен.

## 9. Вердикт

Итог - худший уровень среди причин: «✔ безопасно» (ok), «▲ можно, с условиями» (warn), «✖ нельзя» (bad).

| Уровень | Причина |
|---------|---------|
| bad | PG incomplete: потеря данных |
| bad | PG inactive: встанет I/O |
| bad | OSD выше `full_ratio`: встанет запись на всём кластере |
| bad | OSD выше `backfillfull_ratio`: recovery не завершится |
| bad | PG undersized навсегда (drain, expand, rule, pgnum): failure domain не хватает |
| bad | pgnum: в среднем PG на OSD > `mon_max_pg_per_osd`, монитор отклонит |
| bad | на OSD PG > `mon_max_pg_per_osd` × 3: PG не создадутся |
| bad | rolling: хост нельзя выключить даже в одиночку |
| warn | inactive или incomplete частично из-за PG, неполных уже сейчас: проверьте с `-assume-clean` |
| warn | стало больше OSD выше nearfull, или максимум ближе 3 п.п. к nearfull |
| warn | PG undersized при failure или maintenance |
| warn | на OSD PG > `mon_max_pg_per_osd` и больше, чем было (TOO_MANY_PGS) |
| warn | pg_num не степень двойки; уменьшение pg_num |
| warn | PG остаются на выводимых OSD через `pg_upmap_items` |
| warn | мелкие объекты (< 256 KiB в среднем) на классе без предела по объектам и без mClock: время занижено |
| warn | клиентам не хватит доли mClock: вырастут задержки |
| warn | PG без запаса дольше 4 ч (окно или время recovery) |
| warn | maintenance без noout: окно короче переезда, или данные переедут дважды |

## 10. Сравнение вариантов (`-compare`)

Варианты пересчитываются на той же раскладке, меняются только noout и `osd_max_backfills`:
- maintenance - «с noout», «без noout, backfills 2», «без noout, backfills 6»;
- остальные сценарии - backfills 1, 3, 6.

Лучшим считается вариант с наименьшей оценкой: сначала вердикт, потом меньше переезда, потом быстрее, при равенстве - меньше backfills (бережнее к клиентам):

```
вердикт × 10⁹ + переезд, TB × 10 + время, ч + backfills × 0,5
```

## 11. Отчёт

| Раздел | Что |
|--------|-----|
| шапка | эпоха osdmap, время снимка, число OSD и PG, сценарий, `osd_max_backfills`, описание изменения |
| вердикт | итог и причины |
| Доступность | degraded, inactive, incomplete, без запаса (для сценариев с потерей копий) |
| Перебалансировка | переезд, время, узкое место и его предел, максимальная заполненность, nearfull, PG на OSD, новые OSD |
| Самые заполненные OSD после | 8 OSD: █ сейчас, ▓ прирост, ┊ nearfull и full |
| Конкуренция с клиентским I/O | по классам: нагрузка, доля ёмкости, сколько остаётся recovery |
| Пулы | по каждому пулу: PG, degraded, inactive, без запаса, remapped |
| Сравнение вариантов | при `-compare` |
| План | команды по шагам |
| подвал | откуда скорости слота и предел объектов: калибровка за какой период или значения по умолчанию |
